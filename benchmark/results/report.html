Workloads and controls

  • CPU: 500,000 deterministic arithmetic iterations and 200 rendered rows per page, matching the original reproduction. No external data fetching or artificial delay.
  • Async wait: one 15 ms setTimeout, then 200 cheap deterministic rows. This tests overlap, not network or storage performance. Cross-workload timing is not a like-for-like CPU comparison.
  • Both use canonical slash-ended URLs with trailingSlash: 'always'. Every page must have one request, one 200, and zero redirects. The separate trailing-slash bug cannot inflate these concurrency measurements; the normal reproduction build still uses trailingSlash: 'never'.

Method and validation

  • One unmeasured 20-page build per workload at concurrency 1 and the maximum tested concurrency. Fresh Node processes still have their own JIT warmup.
  • Fresh Node process and removed dist directory per build. Dependencies and OS filesystem caches remain warm; the host is not otherwise isolated.
  • 4 repeats at every condition. Forward/reverse paired orders: 1 → 2 → 4 → 8 → 16; 16 → 8 → 4 → 2 → 1; 4 → 8 → 16 → 1 → 2; 2 → 1 → 16 → 8 → 4.
  • All conditions suppress the same per-page prerender log calls and use the same passive aggregate request observer.
  • Prerender: internal start/end log markers after preview startup and before shutdown. Full build: Vite builder creation through buildApp completion; excludes Node/module startup, cleanup, and output validation.
  • Every page ID and all 200 rendered row values are checked against independently generated expected content outside the timed interval. Complete HTML SHA-256 digests must match across concurrency settings/repeats after replacing only serialized match update timestamps (u:<13-digit milliseconds>); other output assets must match byte-for-byte within each workload/page-count case.

Scope

Synthetic workloads on one local Node preview server. Async control uses setTimeout, not real network/storage. No custom worker pool, Cloudflare adapter, or deployment is measured. Speedups are relative to the same case at concurrency 1, not a comparison between workloads. Synthetic CPU time can still change with JIT warmup, GC, filesystem I/O, host load, and queue overhead. Higher I/O concurrency can help without providing parallel JavaScript CPU execution; this experiment does not implement or time a worker pool.
